# 日期群聊事件回顾设计

日期：2026-10-28  
状态：已确认，进入实施  
目标仓库：`Garden12138/chat-insight`

## 1. 背景与问题

当前「搜索与问答」的 AI 问答基于 RAG：关键词检索与语义向量检索融合，再将排名靠前的有限聊天片段交给模型。该方式适合回答具体问题，但不能保证覆盖指定日期的所有群聊事件。

当前实现中的关键点：

- `src/views/Ask.tsx` 提供 AI 问答与关键词搜索，使用顶部日期范围，并允许选择全部聊天或单个聊天。
- `src-tauri/src/ai/features.rs` 的 `ask()` 调用 `retrieval::retrieve()`，普通问答来源上限为 12 段。
- `src-tauri/src/ai/retrieval.rs` 采用候选截断和 RRF 融合，不是全量时间线扫描。
- `src-tauri/src/ai/store.rs` 已有 AI 文本消息查询、内容估算、指纹与 `ai_cache` 访问能力。
- `src-tauri/src/ai/extraction.rs` 已有可复用的分段/JSON 解析思路，但它的扫描计划含线索词过滤，不能原样用于完整事件回顾。
- `src-tauri/src/ai/indexer.rs` 的 `chunk_messages()` 按时间间隔、消息数和字符数分段，但当前没有强制在 `local_date` 变化时切段。

因此，本功能必须使用数据库日期条件读取完整候选消息，再分段分析；不得依赖 RAG 的 Top-K 结果。

## 2. 产品目标

在「搜索与问答」页面新增「事件回顾」模式，用户选择一个日期与分析范围后，系统分析该范围内所有符合条件的群聊文本消息，生成按时间排序、可回到原始聊天证据的事件时间线。

核心目标：

1. 按 `account_id`、`local_date` 和 `chat_kind='group'` 做数据库硬过滤。
2. 默认分析全部群聊，也支持选择单个群聊。
3. 不依赖语义索引、关键词召回或 Top-K 排名。
4. 所有符合条件的非空文本消息都必须被分段处理；任何失败都要明确展示，不能伪装为完整结果。
5. 每条事件至少关联一条经后端验证的原始消息来源。
6. 保留现有 AI 问答、关键词搜索、约定与待办、群聊决策、聊天详情和年度报告。
7. 在云端模型调用前显示实际分析范围、消息数、字符数、片段数和目标服务，并要求沿用现有云端确认流程。

## 3. 本期范围与非目标

### 本期范围

- 新增事件回顾 UI、日期选择器、群聊范围选择、执行状态和事件时间线。
- 新增本地估算命令、精确读取命令/方法、事件分析命令。
- 分段抽取、来源映射与验证、去重、排序、失败统计、取消与重试。
- 对完整成功结果复用现有 `ai_cache` 缓存机制。
- 修复语义索引分段跨日期问题。
- 对现有 AI 问答增加明确日期约束：若问题包含可确定的日期，该日期必须成为检索硬约束，不能仅作为自然语言提示。
- 当普通 AI 问答输入“2026年10月27日发生了什么事情”这类明确日期 + 事件回顾意图的问题时，自动切换到事件回顾并填入日期；切换应可见，不得静默改写用户选择。若用户当前明确选中了私聊，则不自动执行“全部群聊”回顾。

### 非目标

- 不做跨日/周/月汇总，不做永久事件数据库，不新增数据库 schema 版本。
- 不做图像、视频、音频或附件内容理解；本期只分析 `kind='text'` 且正文非空的消息，并在 UI 中明确说明。
- 不做自动同步后后台扫描。
- 不替代普通 AI 问答，不移除关键词搜索。
- 不保证模型能识别每一件潜在事件；系统要保证的是候选消息覆盖可验证、来源可信、失败透明。
- 不将模型生成内容写入用户的约定或决策记录。

## 4. 已确认的产品行为

### 4.1 模式与筛选

在 `src/views/Ask.tsx` 现有模式切换中增加第三项：

- AI 问答
- 关键词搜索
- 事件回顾

事件回顾提供独立的日期状态与群聊范围状态：

- 日期默认值：当前本地日期。
- 范围默认值：全部群聊。
- 支持选择一个群聊；选项必须只包含 `chatKind === 'group'` 的聊天。
- 不复用普通搜索的 `chatId` 状态，以免搜索私聊筛选意外影响事件回顾。
- 事件回顾使用自己的日期，不受顶部全局日期范围控制；界面需明确提示。
- 当没有符合条件的消息时，显示清晰的空状态，不调用模型。

### 4.2 明确日期问答路由

新增一个可测试的日期/意图解析 helper。MVP 支持：

- `YYYY-MM-DD`
- `YYYY年M月D日`
- `今天`、`昨天`、`前天`（按应用本地日期解析）

不猜测无年份的 `10月27日`，也不将模糊的“最近”“上周”自动转换成某一天。

当普通 AI 问答同时满足“可确定日期”和事件回顾意图（例如“发生了什么”“有哪些事情”“当天事件”“回顾群聊”）时：

- 当前范围为全部聊天：切换到事件回顾，填入解析日期，并在完成必要的云端确认后自动执行事件回顾。
- 当前选中的是群聊：将该群聊设为回顾范围，并在完成必要的云端确认后自动执行事件回顾。
- 当前选中的是私聊：不自动改为全部群聊，保持原有问答行为。
- UI 应明确告诉用户已识别日期并切换到事件回顾。

对于不属于事件回顾意图的具体问题，例如“2026年10月27日谁处理了接口问题”，普通 AI 问答的检索范围必须受该明确日期约束。日期约束与顶部日期范围冲突时，取两者交集；交集为空则不返回其他日期的消息，并给出可理解的提示。

后端必须再次执行日期解析/范围收窄，不能只依赖前端约束。

## 5. 后端设计

### 5.1 数据读取

优先在 `src-tauri/src/ai/store.rs` 中扩展 AI 文本数据访问方法，沿用现有 `TextMessage` 数据类型，避免把 AI 专用消息结构散落到前端或通用数据库层。

建议增加：

- `ai_group_event_messages(account_id, date, chat_id)`：返回符合范围的全部文本消息。
- `ai_group_event_estimate(account_id, date, chat_id)`：返回消息数、字符数、群聊数、片段数等估算数据。
- `ai_group_event_fingerprint(account_id, date, chat_id)`：仅基于实际事件回顾范围生成缓存指纹。

查询必须满足：

- `m.account_id = ?`
- `m.local_date = ?`
- `c.chat_kind = 'group'`
- `m.kind = 'text'`
- `m.text <> ''`
- 如果指定群聊，则 `m.chat_id = ?`
- 排序稳定且按时间递增，例如 `m.occurred_at, m.chat_id, m.local_id`

不得使用 `LIMIT` 截断候选消息。数据库读取应返回全部匹配消息。

### 5.2 事件分析模块

新增 `src-tauri/src/ai/events.rs`，并在 `src-tauri/src/ai/mod.rs` 导出。

建议定义序列化类型：

- `EventReviewEstimate`：`date`、`chat_count`、`message_count`、`chars`、`segment_count`。
- `EventReviewResult`：`date`、`scope`、`events`、`chat_count`、`message_count`、`processed_messages`、`total_segments`、`completed_segments`、`failed_segments`、`complete`、`cancelled`、`cached`、`generated_at`。
- `EventItem`：`id`、`title`、`category`、`summary`、`start_at`、`end_at`、`source_refs`，以及可选的 `scheduled_date`。
- `EventSourceRef`：`chat_id`、`chat_name`、`chat_kind`、`local_id`、`occurred_at`、`sender_name`、`is_from_me`、`text`。

类别枚举建议：

- `announcement`：通知/公告
- `decision`：明确决定
- `task_progress`：任务进度/交付
- `issue`：故障/异常/风险
- `plan`：会议/活动/未来安排
- `information`：有价值的信息分享

模型输出应使用结构化 JSON。每段消息在发送给模型前编号为 `[1]`、`[2]` 等；模型只返回 `source_indices`，由后端映射到该片段的真实消息。不得让模型生成或猜测数据库 ID。

### 5.3 分段规则与覆盖率

- 每个群聊分别按消息时间升序分段，不把不同群聊的消息混为同一个对话上下文。
- 允许按时间间隔和字符数切分，但不得使用线索词过滤片段。
- 每条符合条件的消息必须恰好归属一个待处理片段；通过测试验证无遗漏、无重复。
- 不要静默截断消息正文。超长消息应单独分段；若超出模型上下文导致失败，必须计入失败片段并在结果中展示。
- 每段均应显示进度，例如“正在分析第 4/18 个片段”。
- 每段记录处理成功/失败；模型 JSON 无法解析或来源无法验证时，标记该段失败。
- 取消时返回已完成部分结果，设置 `cancelled=true`、`complete=false`，不缓存为完整结果。
- 失败片段本期不做持久化断点续跑；用户点击重试时重新执行该日期/范围的分析。UI 必须说明结果不完整。

### 5.4 来源验证

模型每条事件的 `source_indices` 必须：

1. 都是当前片段有效的消息编号。
2. 至少有一个有效编号。
3. 映射到当前任务查询到的真实消息。
4. 生成 `source_refs` 时包含 `chat_id + local_id`，不能只用 `local_id`（因为不同群聊可能重复）。
5. 如果事件没有任何有效来源，丢弃该事件并将相应片段标记为失败或记录可诊断的验证错误。

UI 点击来源应复用现有 `MessageContext`，打开正确群聊和原始消息上下文。

### 5.5 去重与排序

- 先做确定性去重：规范化标题、类别、相同来源重叠等。
- 若使用第二轮模型合并事件，只允许输入已提取的事件摘要与受信任来源引用；合并后必须再次校验所有来源引用。
- 对不确定是否同一事件的记录，宁可保留两条，也不要误合并。
- 事件按最早来源消息的 `occurred_at` 升序排序。
- 消息讨论的未来安排不能伪装成当天已经发生的事实；如有可信的明确未来日期，可放入 `scheduled_date`，并将类别标为 `plan`。

### 5.6 命令与缓存

在 `src-tauri/src/ai/commands.rs` 新增：

- `ai_event_review_estimate`：只查本地数据库，不调用模型。
- `ai_review_group_events`：检查 AI 设置和云端授权，执行事件回顾，使用现有 `AiState` 的 stream/cancel 机制。

在 `src-tauri/src/lib.rs` 注册命令。

在 `src/api.ts` 添加对应 API；在 `src/types.ts` 添加类型。

缓存策略：

- 复用现有 `ai_cache`，不新增 schema migration。
- 缓存 key 至少区分 `account_id`、事件回顾 kind、日期/群聊 scope、日期范围和 chat model。
- 指纹只统计本次回顾实际覆盖的群聊范围，不能因为其他私聊消息变化而误认为事件数据变化，也不能漏掉目标群聊新增消息。
- 只有 `complete=true` 且 `failed_segments=0` 的结果才可写入完整结果缓存。
- 缓存命中应标记 `cached=true`；刷新操作应能绕过旧缓存。

## 6. 隐私、权限与取消

- 沿用 `useAi()` 的 `confirmCloud` 和后端 `settings.ensure_allowed(...)`。
- 先调用本地估算命令，再进行云端确认。
- 云端确认说明应包含：日期、全部群聊或指定群聊、消息数、字符数、片段数、目标模型服务/host。
- 未获得同意时不得调用模型。
- 本地模型仍使用现有 AI 开启状态与设置校验。
- 使用 `runAiTask`、`useAiTask`、`stopAiTask` 和 `api.cancelAi(requestId)` 现有任务/取消机制，不另造一套任务框架。
- 在分段循环、每次模型调用前后检查取消状态。

## 7. 修复语义索引日期边界

修改 `src-tauri/src/ai/indexer.rs` 的 `chunk_messages()`：当相邻消息的 `local_date` 不同时，必须先结束当前 chunk，再开始新 chunk。

新增跨午夜/跨日期单元测试，证明一个 chunk 的所有消息属于同一个 `local_date`。这是本次范围内的配套修复，不得借机重写整个索引器。

## 8. 前端结果与交互

在 `src/views/Ask.tsx` 中新增事件回顾界面：

- 日期输入使用现有项目的 UI 风格和可访问标签。
- 范围选项为“全部群聊”与一个指定群聊。
- 显示分析前估算：群聊数、消息数、字符数、片段数。
- 执行时显示当前状态、进度与停止按钮。
- 结果头部显示：完整/不完整/已取消状态，扫描群聊数、候选消息数、成功处理消息数、总片段数、成功片段数、失败片段数、事件数。
- 事件卡片显示类别、时间、标题、摘要、群聊名称和来源入口。
- 失败或取消时显示不完整提示和“重新分析”按钮。
- 没有事件与没有消息是两种不同空状态。
- 结果来源点击后打开 `MessageContext`。
- 模式切换不影响现有 AI 问答与关键词搜索的状态和结果。

## 9. 验收标准

### 数据与范围

- 只读取指定数据集、指定日期、群聊范围内的非空文本消息。
- 全部群聊模式不会混入私聊。
- 指定群聊模式不会混入其他群聊。
- 不存在 Top-K 截断；测试数据超过 12 段时仍全部进入待处理队列。
- 每条符合条件的消息恰好进入一个分析片段。
- 跨日期的语义索引 chunk 不会包含不同 `local_date` 的消息。

### 事件质量

- 所有事件都至少有一个真实来源引用。
- 无效 source index、空标题、非法类别等输入不能进入最终结果。
- 去重不能删除互不相关的事件，也不能丢失合并事件的有效来源。
- 未来安排不得标成已发生的事实。
- 事件按原始来源时间排序。

### 可靠性与隐私

- 估算命令不调用模型。
- 云端未确认时不发送聊天文本。
- 取消与片段失败均显示 `complete=false`。
- 不完整结果不写入完整结果缓存。
- 只有完整成功结果可缓存，数据变化会使缓存失效。
- 普通 AI 问答的明确日期过滤不会返回日期之外的来源。

### 回归与验证

- 现有 AI 问答、关键词搜索、约定与待办、群聊决策、聊天详情、年度报告行为保持正常。
- 执行并修复：`npm run lint`、`npm test`、`npm run build`、`cargo fmt --manifest-path src-tauri/Cargo.toml -- --check`、`cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings`、`cargo test --manifest-path src-tauri/Cargo.toml`。
